## Диагностика доступности Windows/Tk — 01.11.2026

Повторная проверка runtime без создания нового окна: `Python 3.13.7`, `Tkinter/Tk 8.6`, Tcl patchlevel `8.6.15`; встроенная API доступности `tk accessible` относится к Tk 9.1, а runtime 8.6.15 её не содержит. Официальный [Tcl TIP 733](https://core.tcl-lang.org/tips/doc/main/tip/733.md) добавляет для Tk 9.1 API `tk accessible` и связь core/ttk-контролов с системными screen reader API. В нём указано, что Tk не имел встроенной поддержки screen reader до этого изменения; Windows-реализация в основном опирается на MSAA, а мост в UI Automation не считается надёжным. Документация [Python 3.13](https://docs.python.org/3.13/library/tkinter.html) указывает, что официальная сборка Python включает Tcl/Tk 8.6; runtime проекта действительно использует Tk 8.6.15. Страница [Tcl/Tk 9.1](https://www.tcl-lang.org/software/tcltk/9.1.html) описывает эту линию как development work.

**Вывод (по совокупности исходников и наблюдения):** отсутствие доступных имён в текущем Windows UIA-дереве, вероятно, связано прежде всего с базовой возможностью Tk 8.6, а не с одним забытым label-binding в форме. Это вывод, не доказательство работы Tk 9.1 в данном продукте. Tk 9.1 не подменяли; системный Python и существующую сборку не меняли. Следующий технический путь — изолированный proof-of-concept runtime, собранный с Tcl/Tk 9.1, затем проверка совместимости форм/галереи, упаковки и фактического NVDA-сценария.
